# The cost matrix

The stated goal is ten times the performance on a tenth of the resources. That is a claim about every operation, not about fifteen benchmark queries, so it is measured here, where every operation already has a case.

## Why this lives in the compat repository

firepanda-bench measures 37 queries end to end against four engines. It answers whether the engine is competitive on the workloads people publish. It does not tell you that `str.extract` is four times slower than pandas, because no benchmark query calls `str.extract`, and a user whose program is 60 percent string work will discover that on their own.

The conformance suite already calls every operation, on known inputs, with the answers already checked. Adding a timer and a memory high water mark to a harness that does that is a small change, and it produces a table with a row per pandas operation instead of a row per query. That table is the difference between a performance claim and a performance guarantee.

## The budget corpus

The correctness corpus is small and mean, by design, and timing a call on 5 rows measures interpreter overhead. So the budget runs on a second corpus, generated by the same code with a size parameter: 1 million rows by default, 10 million with `--large`, the same dtype mix, the same null shapes, and no edge value placement, since a denormal does not change a runtime and the corpus stays comparable between runs.

Same seed, same generator, same constants, digested in its own manifest at `corpus/budget-manifest.json`. Its own and not the correctness one, which is a change from what this document first said and is here because the correctness manifest digests every value of every column, and doing that to a ten million row frame is a minute of CI time to catch a change that shows up in the first row. The budget digest covers the schema, the row count and 500 rows from each end, which catches a generator change, a dtype change and a size change, and misses a change in the middle. That last one is the price and it is written into the file rather than left for somebody to discover.

The manifest is keyed by size, because the corpus at one size is not the corpus at another and a single digest could not describe both. What is true across sizes is that the stream is a counter stream, so the first thousand rows at ten thousand are the first thousand rows at one thousand and a result at one size can be read next to a result at another. The one exception is the unique key column, whose bound is the row count by design, and there is a test that says so.

The frames are written to Arrow IPC under `corpus/budget/<rows>/` and loaded through the same engine method the correctness corpus uses, so the Mojo driver needs nothing new to run the matrix. Two corpora and one loader, because a second loader would be a second place for two engines to disagree about what they were handed.

## The measurement

One process per engine per operation, per the same rule the bench repository uses, because peak resident set is a property of a process and two engines in one interpreter cannot both be measured.

Per operation the worker reports wall clock, peak resident set, resident set delta over the call, user and system CPU, page faults, and the thread count actually used. Seven repeats, median reported, interquartile range published. The input is materialized and the answer is consumed before the timer stops, so nothing is measured lazily that would not be paid for by a user.

The published cell is a pair of ratios against pandas, time and peak memory, and the sign convention is that above 1 is better for time and above 1 is better for memory:

```
| Operation                | pandas ms | firepanda ms | speed | pandas MB | firepanda MB | memory |
|--------------------------|-----------|--------------|-------|-----------|--------------|--------|
| groupby.sum 1e6 x 1e3    |      31.4 |          2.6 | 12.1x |       118 |           24 |   4.9x |
| str.contains literal     |      44.0 |          3.1 | 14.2x |        96 |           31 |   3.1x |
| sort_values 1e6 int64    |      66.2 |         12.9 |  5.1x |       142 |           40 |   3.6x |
| astype float64->int32    |       2.9 |          2.4 |  1.2x |        24 |           16 |   1.5x |
```

The fourth row is the one that makes the table worth publishing.

## What ten times and a tenth actually mean

The goal is right as an ambition and it is wrong as a uniform expectation, and saying which is which now is cheaper than being asked later.

**Where ten times is available.** Anything that pandas runs on one core and firepanda runs on all of them, which is most grouped work, most sorting and most string work, gives between 8 and 30 times on a machine with enough cores, and the multiple is mostly the core count. Anything where pandas materializes a Python level intermediate, which is `apply`, `map` and the object dtype paths, gives more than 100 times because the comparison is against an interpreter. Anything that is algorithmically better, such as a radix partitioned aggregation against a hash table per column, gives a factor on top of the core count.

**Where ten times is not available.** A single pass over one column that does nothing but copy bytes is bandwidth bound in both libraries, and the ceiling is the memory controller, not the language. `astype` between two fixed width types, `abs`, a comparison against a scalar, and anything else that reads n bytes and writes n bytes lands between 1 and 3 times, and no amount of work moves it, because pandas 3.0 dispatches those to Arrow compute which is already vectorized C++. Publishing 1.2 times on those rows is the honest thing to do and it is also the useful thing, because it tells a user that a program dominated by casts will not get faster and they should stop reading.

**Where a tenth of the memory is available.** Peak memory in pandas is dominated by intermediates, so a chunked engine that never materializes a whole intermediate column wins by a large factor on any chain of more than two operations, and by very little on a single operation whose output is the same size as its input. The interesting rows are therefore the multi step ones, and the matrix includes 20 chained cases for exactly that reason: filter then group, join then aggregate, read then cast then sort. Those are where the tenth is real.

**Where a tenth of the memory is not available.** An operation whose output is as large as its input cannot use much less than two columns of memory in any implementation. Sorting needs a permutation and a destination. A join output larger than either input is larger than either input in every engine. Those rows will read between 1.5 and 3 times and the number is the truth.

So the goal restated in a form that can be met and checked: **the median across the matrix is ten times on time and five times on peak memory, the chained cases are ten times on both, and no row is slower than pandas.**

That last clause is the one that matters day to day. A row below 1.0 is a performance bug with a name and an input size, and it goes on the issue list the day it appears. That is a thing this project can promise and the uniform ten times is not.

## The gate

Like the conformance ratchet: no row may regress by more than 10 percent against the committed baseline without a line in the pull request saying why. The baseline is per machine, and the two machines are the ones firepanda-bench already uses, an AMD EPYC VPS and an i9-13900K desktop, because a second set of machines would mean a second set of noise to characterize.

The matrix runs nightly rather than per pull request. It takes 20 minutes at 1 million rows across the whole registry and that is too slow for a merge gate, and a per pull request subset of 40 operations chosen for coverage runs in 2 minutes and is the gate.

Two things about the gate that the first implementation settled and this document should say. It does not run in CI. A timing gate on a shared runner fails on a noisy neighbour and passes on a real regression that happened to land on a quiet one, and after the third false alarm somebody adds a retry and it stops being a gate. So `pixi run budget-gate` belongs on a machine that is always the same one, and what CI runs is the whole matrix at ten thousand rows with one repeat, where every timing is noise and the only thing being checked is that all 53 operations are still spelled correctly against the pinned pandas.

And a row that stopped running counts as a regression. An operation that used to work and now raises is the largest regression available, and a gate that only compares the rows both sides have would score it as a clean pass.

## The table other repositories read

The matrix is measured here and it is read elsewhere. firepanda-bench wants to say which operations a benchmark query is made of, so that a reader who sees a query where firepanda loses can find out which operation inside it lost, and it cannot import this package: a bench environment carries Polars, DuckDB and cuDF and this one deliberately carries none of them.

So the operation table is committed as `operations.json`, the same way the pandas inventory is committed, and the other repository vendors a copy. It is the id, the section, the pandas names the operation covers and whether it is a chain, and it has no numbers in it at all. A timing belongs to a machine and this file belongs to a commit, so a median published here would be a number people quote with the machine detached from it. CI checks the file against the registry, because a row added or renamed without a diff is a link in the other repository that quietly points at nothing.

## The rule

Same one as everywhere else in these two repositories. **Publish the rows we lose.** A cost matrix where firepanda wins every row has either been curated or is measuring the wrong thing, and the first person to notice will be somebody deciding whether to trust the project.
