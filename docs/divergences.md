## engine/regex-lookaround

This entry has been narrowed twice and what is left under it has nothing to do with a lookaround, which is why the id is kept rather than corrected: an id here is a promise made to users and renaming one silently breaks every link to it. It used to say that a backreference and a lookaround were both refused, because firepanda's engine has RE2 semantics and RE2 has neither, and that the linear time guarantee was what the refusal bought. Both are answered now and the guarantee is intact, because the answer was never to give the whole engine backtracking. A backreference is run by a bounded backtracker chosen by the program rather than by the row, so a pattern that holds one pays for it and no other pattern does. Then it said that the two constructs written beside each other were still refused, because the machine that runs the body of an assertion is the ordinary machine and cannot read a backreference, a cut or a test. That is answered too: the backtracker runs the inner search itself, on the stack it already has, from the height the stack stood at when the body started. The eight cases that asserted the two refusals moved to fpcompat/cases/strings.py and score. What is left is that RE2 runs on bytes, so it answers a non word boundary at a position halfway through a character, and standing where no character begins is a different engine rather than a missing construct.

## engine/zero-divisor

Dividing an integer by zero has no answer, and the two engines disagree about what to write in the row that has none. pandas promotes the whole column to float64 and writes an infinity or a NaN, which costs every other row in that column its type: an int64 column with one zero divisor in it comes back float64, and every value in it above two to the fifty third is then silently rounded, so one bad row damages the good ones. firepanda writes a null, which is the value the format already has for a row with no answer, and keeps the column's width, so the rows that divided exactly stay exact. True division is not affected and is not registered here, because its answer is a float64 whatever the divisor is and there is no type to lose. The bool remainder is the one place this is visible outside the integer widths: pandas answers int8 zeros for `flag % flag` because the bool path skips the masking it applies to the integer dtypes, and firepanda widens to int8 and answers a null at the zero divisor like every other integer column.

**Instead.** the row divided by zero is null and the column keeps the dtype it started with. Floor division and the remainder on an int64 column answer int64, and `flag % flag` on two bool columns answers int8 nulls rather than int8 zeros.

## engine/string-count-width

How many characters a row has and where a substring sits in it are both integers, and both are unanswerable on a row that is missing. pandas has nowhere to put that in a numpy int64 array, so it widens the whole column to float64 and writes a NaN, and every count in the column becomes a float because one row had nothing to count. firepanda answers int64 with a null in that row, which is the type the question has and the value the format already has for a row with no answer. The cost of the pandas answer is not theoretical: a position above two to the fifty third does not survive the trip through a float, and a caller who wanted to index with the number gets a float back and has to cast it. A column with no missing rows in it is int64 in pandas too, which is why this entry names one frame: on the other three text frames the two engines agree to the last bit and the suite requires them to.

**Instead.** str.len, str.find, str.rfind and str.count answer int64 with a null on a missing row, rather than float64 with a NaN. The counts and positions themselves agree. str.count joined the entry when it landed rather than being registered on its own, because how many times a pattern appears in a row that is not there is the same unanswerable question as how long that row is, and it is answered here the same way.

## engine/window-infinity

pandas cannot get an infinity back out of a window and firepanda can, and the reason is one line of Python rather than a property of any kernel. The last thing pandas.core.window.rolling.BaseWindow._prep_values does before handing the column to a kernel is three lines under the comment `Convert inf to nan for C funcs`, which replace every infinity in the column with a NaN. So an infinity in a pandas rolling or expanding window is a missing value, and the window is reduced over the rows either side of it. Measured on pandas 3.0.3, the expanding sum over the suite's own float64 frame answers the largest finite double from row five onward, where the window holds both a positive and a negative infinity and the arithmetic says NaN, and it answers that same finite number where the window holds only one of them and the arithmetic says an infinity. The extremes go the same way for the same reason, so an expanding max over a column whose second row is a positive infinity answers the largest finite value it has seen instead, for every row after it. count is the one reduction of the ten that does not see the replacement, because it reads the presence indicator rather than the values, so pandas will report that a window holds two values and then answer the sum of one of them. This is the window layer and not pandas as a whole: pd.Series([1.0, float('inf')]).sum() is an infinity and .max() is an infinity, and only rolling and expanding lose them. firepanda counts the two infinities beside the finite total and assembles the answer from the three at the end, and its extremes treat an infinity as the ordinary value it is, so both survive the row that carried them leaving the window again.

**Instead.** a window that holds an infinity answers that infinity, a window that holds one of each sign answers a NaN, and both are still right after the row that carried the infinity has left the window again. Every window with no infinity in it agrees with pandas to the last bit, which is why this entry names two frames and not the other two the same cases run on.

## engine/window-spread-overflow

A rolling variance is carried from one window to the next in both engines, because recomputing it would cost the width of the window on every row, and a carried sum of squared deviations can overflow. Row five of the suite's float64 frame is the largest finite double, so the first three eight row windows that are full and reach it overflow in both engines, both answer an infinity, and the suite requires them to agree there. Row thirteen is the first window that has let go of that value again. firepanda checks the error bound it carries beside the sum before it answers, an infinite sum fails that check, and it rebuilds from the eight rows in front of it and answers 8.758845844921883e+30. pandas carries the infinity forward and answers an infinity for that row and for the fifty remaining rows of the frame, so 51 of the 64 rows differ and every one of them is a row where the window holds nothing unusual. The bound firepanda carries is not only for this: it fires whenever a value much larger than the rest leaves the window and the running answer has lost its meaning, which happens on ordinary data and not only at the top of the float range.

**Instead.** a window whose sum of squared deviations overflowed is rebuilt from its own rows once the value that overflowed it has left, so the answer is finite again as soon as the data is. The row that genuinely overflows still answers an infinity, because that is what the arithmetic over those eight values says. On the tall frame these three cases also run on there is nothing near the top of the float range, nothing overflows, and the two engines agree to the last bit.

## engine/window-shape-overflow

## engine/ewm-infinity

The difference engine/window-infinity describes, on the third window type. ExponentialMovingWindow is a BaseWindow, so the three lines of _prep_values that replace every infinity with a NaN under the comment `Convert inf to nan for C funcs` run before an exponentially weighted mean as well, and an infinity in a pandas ewm is a missing row. What makes this its own entry rather than a longer case list on that one is that an exponentially weighted window never drops a row, so the recovery the rolling entry describes cannot happen the same way. Exactly one of the sixty four rows differs here, and the reason it is one rather than all of them is worth writing down. Row one of the frame is a positive infinity and row two is a negative one. At row one firepanda answers the positive infinity and pandas, having seen nothing at all, answers NaN. At row two the fold reaches an infinity plus its negative, firepanda's carried value becomes a NaN, and both engines answer NaN for the same row by two different routes. From row three on they agree to the last bit for the remaining sixty one rows, because the test pandas' own kernel uses for whether the recurrence has started is whether the carried value equals itself, firepanda copies that test, and a cancelled infinity therefore reads as nothing having arrived yet and the row after it starts the recurrence again from its own value. Measured on pandas 3.0.3 for all six cases, and the exponentially weighted total goes the same way as the four means for the same reason. The var and std cases on this frame are not listed, because both engines lose the answer to an overflow in the squared deviation of the largest finite double and agree exactly on every row.

## engine/ewm-infinity-carried

The same replacement as engine/ewm-infinity and the opposite outcome, because on this frame there is only one infinity in reach and a lone infinity never cancels. The half null frame holds a NaN in row zero, nothing in row one, a negative infinity in row two and then a value in every second row. So firepanda's recurrence starts at the negative infinity, and the weighted average of an infinity and a finite number is that infinity however small the weight behind it has become, so every remaining row of the column answers negative infinity. pandas replaced the infinity before the kernel ran, so its recurrence starts at the smallest denormal in row four and climbs through ordinary values near ten to the fifteen. Sixty two of the sixty four rows differ under ignore_na, which is every row from the infinity onward, and fifty eight differ under the min_periods case, which is the same thing starting later because a count of three is not met until the third value arrives at row six. This is one entry over two cases rather than two entries because the two are the same difference at two starting rows, and neither of them recovers. Measured on pandas 3.0.3, where row eight of the min_periods case is 4898424505258373.0 against a negative infinity here.

## engine/pandas-exception-classes

pandas defines about forty six exception classes of its own in pandas.errors, and no firepanda exception can be a subclass of any of them, because inheriting from one means importing pandas and a replacement for pandas is the one library that cannot depend on pandas. Both cases here refuse the operation, both refuse it for the reason pandas refuses it, and both say so in a message that leads with pandas' own sentence. What differs is the class on the object. Casting a column holding a null to an integer raises firepanda.errors.IntCastingNaNError, which has the same name as pandas.errors.IntCastingNaNError and is an unrelated class, and both of them are a ValueError underneath, so a caller who catches the builtin is unaffected and only a caller who names the pandas class is. Too many indexers raises firepanda.errors.InvalidArgumentError where pandas raises pandas.errors.IndexingError, and there the builtin underneath differs as well, since pandas' IndexingError inherits from Exception directly and ours is a ValueError. A merge with no key to join on, with keys that fail validate, or with a key on a cross join, raises firepanda.errors.MergeError, which is a ValueError as pandas.errors.MergeError is, and is otherwise the same story as IntCastingNaNError. A query that names something it cannot read raises firepanda.errors.UndefinedVariableError, which is a NameError as pandas.errors.UndefinedVariableError is, and carries pandas' own message word for word. Restating instants in nanoseconds when one of them is out of that range raises firepanda.errors.OutOfBoundsDatetime, which is a ValueError as pandas.errors.OutOfBoundsDatetime is, and names the same instant in the same sentence. A row with too many fields raises firepanda.errors.ParserError and an empty file raises firepanda.errors.EmptyDataError, which are a ValueError as pandas' two are and carry pandas' messages word for word. A window reduction over a column that is not numbers raises firepanda.errors.DataError, which inherits from Exception directly as pandas.errors.DataError does, and carries pandas' sentence word for word. This is one entry over several cases rather than one each because they are one fact about the dependency graph and not two facts about indexing and about casting, and every further case the suite writes that names a pandas defined class belongs on this list.
