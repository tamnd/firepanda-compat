## engine/plotting

Plotting and styling are a different library's job. pandas ships a matplotlib front end and an HTML styler, and both of them are presentation layers built on top of a dataframe rather than parts of one. firepanda raises on every plotting and styling name with a message pointing at to_pandas(), which is a one line change for a user who wants a chart and several thousand lines the library would otherwise have to carry forever.

## engine/pickle

Reading a pickle executes whatever code is in it, so read_pickle on an untrusted file is arbitrary code execution with a friendly name. It also pins the file format to the exact class layout of the version that wrote it, which means a pickle is unreadable by any other tool and often by a later pandas. firepanda raises with a pointer to Parquet and Arrow IPC, both of which another program can read and neither of which runs anything on load.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

## engine/object-dtype

A column of arbitrary Python objects is a column with no type, no memory layout and no vectorized operation available to it. Every operation on one becomes a loop that reaches into the interpreter once per element, which is where the ten to one performance difference this project exists for disappears. firepanda raises at construction, naming the column and the offending Python type, so the user finds out at the point they can still fix it rather than after their program is written.

## engine/inplace

## engine/moment-precision

The variance, the standard deviation, the standard error and the skewness are computed from deviations around each group's mean, and the mean is a sum divided by a count, so it is near the true mean and is not it. pandas leaves that error in. firepanda sums the plain deviations alongside the squared ones and subtracts the residual, which costs one addition per row and makes the answer independent of how accurate the centre was. On ordinary columns the two agree to the last bit and the correction is worth nothing. On a column of large values with a small spread it is worth a great deal, and the two engines part company: on five values at two to the fifty second pandas gives a variance of 37.25 where the true value is 37.2, and a skewness of 1.4863469519931585 where the true value is 1.3253147098134046, which is twelve percent. This entry is about a float column, where the values are exact and only the centre can be wrong. An integer column has a second source of error before the centre is taken, and that one is engine/integer-moments.

**Instead.** the moments are corrected for the centre they were measured around, so the answer does not change when a constant is added to the column. Where the two disagree, firepanda is the one nearer the value exact arithmetic gives.

Kind `engine`, since 2026-09-05, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

## engine/zero-divisor

Dividing an integer by zero has no answer, and the two engines disagree about what to write in the row that has none. pandas promotes the whole column to float64 and writes an infinity or a NaN, which costs every other row in that column its type: an int64 column with one zero divisor in it comes back float64, and every value in it above two to the fifty third is then silently rounded, so one bad row damages the good ones. firepanda writes a null, which is the value the format already has for a row with no answer, and keeps the column's width, so the rows that divided exactly stay exact. True division is not affected and is not registered here, because its answer is a float64 whatever the divisor is and there is no type to lose. The bool remainder is the one place this is visible outside the integer widths: pandas answers int8 zeros for `flag % flag` because the bool path skips the masking it applies to the integer dtypes, and firepanda widens to int8 and answers a null at the zero divisor like every other integer column.

**Instead.** the row divided by zero is null and the column keeps the dtype it started with. Floor division and the remainder on an int64 column answer int64, and `flag % flag` on two bool columns answers int8 nulls rather than int8 zeros.

Kind `engine`, since 2026-09-06, specified in `06-pandas-parity.md#the-genuine-omissions`.

## engine/category-code-width

pandas picks the width of a categorical's codes from how many categories there are, so a column of three categories gets int8. firepanda writes int32 whatever the count is. Picking from the cardinality means the same column encodes to a different Arrow type on different data, so a program that reads the codes has no type to write down and a file written on Monday does not have the schema of the one written on Tuesday. It is also visible through the Arrow export, which is the boundary this library is built on, so it is a decision about the dtype vocabulary rather than one about the encoder. The values agree either way, and a program comparing codes to codes is unaffected. The one that is affected is a program comparing dtypes, and that program is better off finding out.

**Instead.** the codes are int32 whatever the number of categories, and a code for a row whose category is missing is null rather than the sentinel minus one, because firepanda's codes are an Arrow column with a validity bitmap and pandas' are a numpy integer array with nowhere to record absence.

Kind `engine`, since 2026-09-11, specified in `27-what-a-caller-does-with-a-category.md#three-differences-from-pandas-all-of-them-deliberate`.

## engine/string-count-width

How many characters a row has and where a substring sits in it are both integers, and both are unanswerable on a row that is missing. pandas has nowhere to put that in a numpy int64 array, so it widens the whole column to float64 and writes a NaN, and every count in the column becomes a float because one row had nothing to count. firepanda answers int64 with a null in that row, which is the type the question has and the value the format already has for a row with no answer. The cost of the pandas answer is not theoretical: a position above two to the fifty third does not survive the trip through a float, and a caller who wanted to index with the number gets a float back and has to cast it. A column with no missing rows in it is int64 in pandas too, which is why this entry names one frame: on the other three text frames the two engines agree to the last bit and the suite requires them to.

**Instead.** str.len, str.find, str.rfind and str.count answer int64 with a null on a missing row, rather than float64 with a NaN. The counts and positions themselves agree. str.count joined the entry when it landed rather than being registered on its own, because how many times a pattern appears in a row that is not there is the same unanswerable question as how long that row is, and it is answered here the same way.

## engine/window-infinity

pandas cannot get an infinity back out of a window and firepanda can, and the reason is one line of Python rather than a property of any kernel. The last thing pandas.core.window.rolling.BaseWindow._prep_values does before handing the column to a kernel is three lines under the comment `Convert inf to nan for C funcs`, which replace every infinity in the column with a NaN. So an infinity in a pandas rolling or expanding window is a missing value, and the window is reduced over the rows either side of it. Measured on pandas 3.0.3, the expanding sum over the suite's own float64 frame answers the largest finite double from row five onward, where the window holds both a positive and a negative infinity and the arithmetic says NaN, and it answers that same finite number where the window holds only one of them and the arithmetic says an infinity. The extremes go the same way for the same reason, so an expanding max over a column whose second row is a positive infinity answers the largest finite value it has seen instead, for every row after it. count is the one reduction of the ten that does not see the replacement, because it reads the presence indicator rather than the values, so pandas will report that a window holds two values and then answer the sum of one of them. This is the window layer and not pandas as a whole: pd.Series([1.0, float('inf')]).sum() is an infinity and .max() is an infinity, and only rolling and expanding lose them. firepanda counts the two infinities beside the finite total and assembles the answer from the three at the end, and its extremes treat an infinity as the ordinary value it is, so both survive the row that carried them leaving the window again.

**Instead.** a window that holds an infinity answers that infinity, a window that holds one of each sign answers a NaN, and both are still right after the row that carried the infinity has left the window again. Every window with no infinity in it agrees with pandas to the last bit, which is why this entry names two frames and not the other two the same cases run on.

## engine/rolling-max-varargs

pandas declares Rolling.max as (numeric_only=False, *args, engine=None, engine_kwargs=None, **kwargs) and it is the only one of the ten window reductions that does. Rolling.sum, Rolling.mean, Rolling.min and all five of the Expanding ones take numeric_only, engine and engine_kwargs and nothing else, and Expanding.max takes exactly those three as well. The two extra parameters are not read. The body of the method is a single call to super().max(numeric_only=..., engine=..., engine_kwargs=...), so args and kwargs are collected and dropped, and s.rolling(2).max(False, out=None) silently ignores out rather than refusing it. Their documentation in the method's own docstring says they are positional and keyword arguments passed into func, and there is no func in a maximum. firepanda declares the same three parameters on all ten reductions, which means nine of the ten match pandas exactly and this one does not. Copying the accident would mean writing a signature that accepts anything and ignores it, which is the one thing this library refuses to do everywhere else, and it would have to be written on Rolling.max alone to be faithful, so the generator that emits one table for both classes would gain a special case for a parameter nobody can use.

**Instead.** Rolling.max takes numeric_only, engine and engine_kwargs, the same three the other nine reductions take, and refuses anything else by name. A caller who was relying on the extra parameters was relying on pandas throwing them away.

Kind `engine`, since 2026-09-11, specified in `31-a-window-is-a-pair-of-rows.md#the-python-surface-and-the-four-arguments-that-are-declared-and-refused`.

## engine/window-spread-overflow

A rolling variance is carried from one window to the next in both engines, because recomputing it would cost the width of the window on every row, and a carried sum of squared deviations can overflow. Row five of the suite's float64 frame is the largest finite double, so the first three eight row windows that are full and reach it overflow in both engines, both answer an infinity, and the suite requires them to agree there. Row thirteen is the first window that has let go of that value again. firepanda checks the error bound it carries beside the sum before it answers, an infinite sum fails that check, and it rebuilds from the eight rows in front of it and answers 8.758845844921883e+30. pandas carries the infinity forward and answers an infinity for that row and for the fifty remaining rows of the frame, so 51 of the 64 rows differ and every one of them is a row where the window holds nothing unusual. The bound firepanda carries is not only for this: it fires whenever a value much larger than the rest leaves the window and the running answer has lost its meaning, which happens on ordinary data and not only at the top of the float range.

**Instead.** a window whose sum of squared deviations overflowed is rebuilt from its own rows once the value that overflowed it has left, so the answer is finite again as soon as the data is. The row that genuinely overflows still answers an infinity, because that is what the arithmetic over those eight values says. On the tall frame these three cases also run on there is nothing near the top of the float range, nothing overflows, and the two engines agree to the last bit.

## engine/window-spread-infinity

An expanding window never lets go of a row, so the positive infinity in row one and the negative infinity in row two are inside every window from row one to the end of the frame and there is no recovery to argue about. firepanda answers NaN for all of them, which is what a spread around a mean that is not a number is. pandas replaces both infinities with missing values before the kernel runs, for the reason engine/window-infinity gives, so it sees a column that is two rows shorter instead. At row four its window holds a negative zero and the smallest denormal and it answers zero where firepanda answers NaN. At row five the largest finite double arrives, pandas' sum of squared deviations overflows, and pandas answers an infinity for the remaining fifty nine rows. So 60 of the 64 rows differ, and only row four is the replacement showing on its own rather than with an overflow on top of it. The replacement is visible in smaller data too: rolling(2, min_periods=1).var(ddof=0) over 1.0, an infinity, 2.0, 3.0 and 4.0 answers zero in the row that holds the infinity, on the reasoning that a window with one value in it has no spread, and firepanda answers NaN there.

**Instead.** a window that holds an infinity has no mean and therefore no spread, so var, std and sem answer NaN, and they keep answering it for as long as the infinity is in reach. An expanding window never drops a row, so that is every row after the one that carried it. On the tall frame these three cases also run on there is no infinity in the column and the two engines agree to the last bit.

## engine/window-shape-overflow

A skewness is a third central moment over a three halves power of the second and a kurtosis is a fourth over a square, and pandas builds both from running sums of the raw powers of the values. Row five of the suite's float64 frame is the largest finite double, so its cube and its fourth power are infinities the moment they are formed, and every sum they enter is an infinity from then on. pandas therefore answers NaN for all sixty four rows of the frame, including the fifty one that hold nothing but ordinary values near ten to the fifteen. firepanda carries the central moments themselves with an error bound beside each, so the bound catches the window that overflowed, the window is rebuilt from its own eight rows as soon as that value has left, and row thirteen onwards answer. At row thirteen firepanda gives a skewness of 0.16153873394877702 where exact rational arithmetic over those eight values gives 0.16153873394877818, so it is right to fifteen figures and pandas has no answer. 51 of the 64 rows differ and every one of them is a row where the window holds nothing unusual.

**Instead.** a window whose moments overflowed is rebuilt from its own rows once the value that overflowed them has left, so the shape is a number again as soon as the data is. The rows that genuinely hold the largest finite double still answer NaN, because a fourth moment over those eight values is an infinity whichever way it is computed. On the tall frame these two cases also run on there is nothing near the top of the float range and the two engines agree to within the suite's statistical tolerance.

## engine/pandas-exception-classes

pandas defines about forty six exception classes of its own in pandas.errors, and no firepanda exception can be a subclass of any of them, because inheriting from one means importing pandas and a replacement for pandas is the one library that cannot depend on pandas. Both cases here refuse the operation, both refuse it for the reason pandas refuses it, and both say so in a message that leads with pandas' own sentence. What differs is the class on the object. Casting a column holding a null to an integer raises firepanda.errors.IntCastingNaNError, which has the same name as pandas.errors.IntCastingNaNError and is an unrelated class, and both of them are a ValueError underneath, so a caller who catches the builtin is unaffected and only a caller who names the pandas class is. Too many indexers raises firepanda.errors.InvalidArgumentError where pandas raises pandas.errors.IndexingError, and there the builtin underneath differs as well, since pandas' IndexingError inherits from Exception directly and ours is a ValueError. A merge with no key to join on, or with keys that fail validate, raises firepanda.errors.MergeError, which is a ValueError as pandas.errors.MergeError is, and is otherwise the same story as IntCastingNaNError. A query that names something it cannot read raises firepanda.errors.UndefinedVariableError, which is a NameError as pandas.errors.UndefinedVariableError is, and carries pandas' own message word for word. Restating instants in nanoseconds when one of them is out of that range raises firepanda.errors.OutOfBoundsDatetime, which is a ValueError as pandas.errors.OutOfBoundsDatetime is, and names the same instant in the same sentence. This is one entry over several cases rather than one each because they are one fact about the dependency graph and not two facts about indexing and about casting, and every further case the suite writes that names a pandas defined class belongs on this list.

## engine/dtype-spelling

Every type firepanda has is an Arrow type and dtype gives Arrow's name for it, while every type pandas has is a numpy dtype or a pandas extension dtype and dtype gives that one's name. For most types the two vocabularies happen to share a word, so int64, float64, bool and category read identically on both sides and nobody notices there are two vocabularies at all. Text and dates are where they do not share a word. A column of text is string here, which is Arrow's name, and str in pandas 3, which is the name of the extension dtype that replaced object in that release. A column of dates carrying a day and no clock is date32[day] here and object in pandas, because pandas has no date dtype and reads such a column into a column of Python date objects, which is the one representation it refuses to have anywhere else and which firepanda refuses outright. There is no third name that would be right for both, and translating Arrow's names into pandas' at the boundary would mean a user cannot ask a firepanda column what it is and get an answer that is true of the memory underneath it. The timestamp case beside these two is the control and has to pass, because pandas does have a dtype for a timestamp and both libraries call it datetime64[s]. The frame list on this entry is what keeps it honest. The whole frame member runs over the corpus shapes and over the wide, temporal and categorical frames, and it is only allowed to differ on the three shapes that carry a text column and on the frame that carries a date column. On the wide frame of int64 columns and on the categorical frame it has to agree exactly, so an entry written to excuse two words cannot quietly excuse a type system.

**Instead.** a column is named by its Arrow type, so text is string rather than str and a date is date32[day] rather than object. Types that both vocabularies have a word for are spelt the same way on both sides.

## engine/nbytes

A byte count here and a byte count in pandas are answers to two different questions that happen to share a name. firepanda counts the Arrow buffers the data is actually stored in: the values, the validity bitmap, the views and the payload for text, and both the codes and the categories for a dictionary column. pandas counts the size of the numpy representation, so a column of three strings is twenty four bytes of pointers plus whatever pandas 3 has started adding for the characters, and the labels of a frame that never declared any are one hundred and thirty two bytes, which is the size of the three Python integers a RangeIndex holds and is a fact about a Python object rather than about any data. Neither number is wrong and neither can be converted into the other. The two do not agree even on a dense integer column, because Arrow allows a column with no nulls to omit its validity buffer and firepanda allocates one anyway, so a sixty four row int64 column is one byte heavier here than the numpy array holding the same values. What a caller should do about it is compare each number against the right thing: this one is close to the size of the same data in an uncompressed Parquet file and close to what the process grows by when the frame is loaded, and pandas' is close to neither of those once there is text in the frame. Anybody who needs the pandas number has to_pandas().memory_usage(). The labels case beside these is the control and has to pass, because the shape of the answer is pandas' down to the index row coming first under the label Index, and only the counting under those labels differs.

**Instead.** the count is the bytes in the Arrow buffers, so the text in a text column is inside the number, an index nobody declared weighs nothing, and a column with no nulls still pays for the validity bitmap it was allocated.

## engine/missing-spelling

pandas does not have a spelling for a missing value, it has four, and which one a column gives you says what that column is made of rather than what happened to the row. A numpy float array has nowhere to record absence, so the hole is the floating point NaN itself and prints NaN. A timestamp plays the same trick with a sentinel integer and prints NaT. An object column holds the Python object and prints None. And every one of pandas' nullable types, which keep absence in a mask beside the values, prints <NA>. Every firepanda column is an Arrow array with a validity bitmap, so the closest thing pandas has to a firepanda column is a pyarrow backed one, and pandas prints <NA> for that. The spelling here is pandas' own word for a column that works the way ours do, not a word this library invented. A float column used to be under this entry as well and is not any more, because DataFrame.from_arrow reads a float gap as NaN the way pandas does, so a float column read that way prints NaN and reads out as nan on both sides. What it costs is width: <NA> is one character longer than NaN, so a column with a gap in it is one wider here and every value in it moves one place, which is why the printing cases in the basics section were written to stay off the null bearing frames until this entry existed.

**Instead.** a missing value is written <NA> whatever the column holds, where pandas writes NaN on a text column, NaT on a temporal one and <NA> only on its nullable types. Read out as a Python object it is None rather than nan or NaT. Asking whether a value is missing agrees on both sides, including on a genuine NaN.

## engine/integer-column-labels

A pandas column label can be any hashable object and a firepanda column label is text. That is a decision about what a schema is rather than an omission: an Arrow schema names its fields with strings, every firepanda frame is an Arrow frame, and a label type that allowed integers would have to be carried through the schema, the Arrow export, the C Data Interface and every place a frame is written to a file, in exchange for letting a user write df[0] instead of df['0']. So an integer label arrives as the text of that integer. Nothing is lost, nothing is reordered, and no value under a label changes. Two places make it visible. A frame built from a dictionary with integer keys gets text labels here, which is the general form. **Instead.** a column label is always text, so an integer label is the text of that integer, and the three columns of a partition are labelled '0', '1' and '2' where pandas labels them 0, 1 and 2.

## engine/integer-moments

pandas computes a skewness by casting the column to float64 first and measuring every value from the mean afterwards. The two int64 corpus frames sit near minus two to the sixty second with a spread of about four billion, and down there neighbouring float64 values are a thousand and twenty four apart, so the cast moves each value by up to five hundred and twelve before the arithmetic starts. A variance hardly notices, because the error is small against the spread and enters squared. A skewness notices in its seventh digit, because the third moment of a column that is nearly symmetric is a small difference of large sums. firepanda measures each value from a whole number beside the mean as an integer, which is exact, and casts only the difference, which is small enough to be a float without rounding. Measured with exact rational arithmetic, the true skewness of int64_no_nulls is 0.24718404221495238, pandas answers 0.2471839475025952, which is 3.8e-7 out, and firepanda answers the true value. On int64_half_null the true value is 0.1205624517525931 and pandas is 5.8e-6 out. Every other frame the case runs on is either a float column or small enough that the cast is exact, and on those the two agree.

**Instead.** the skewness of an integer column is measured before the values are rounded to float64, so on a column of large integers with a small spread it is the value exact arithmetic gives and pandas' is a few parts in ten million away.
