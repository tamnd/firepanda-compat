## engine/plotting

Plotting and styling are a different library's job. pandas ships a matplotlib front end and an HTML styler, and both of them are presentation layers built on top of a dataframe rather than parts of one. firepanda raises on every plotting and styling name with a message pointing at to_pandas(), which is a one line change for a user who wants a chart and several thousand lines the library would otherwise have to carry forever.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

## engine/pickle

Reading a pickle executes whatever code is in it, so read_pickle on an untrusted file is arbitrary code execution with a friendly name. It also pins the file format to the exact class layout of the version that wrote it, which means a pickle is unreadable by any other tool and often by a later pandas. firepanda raises with a pointer to Parquet and Arrow IPC, both of which another program can read and neither of which runs anything on load.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

- `divergences/pickle/*`

## engine/object-dtype

A column of arbitrary Python objects is a column with no type, no memory layout and no vectorized operation available to it. Every operation on one becomes a loop that reaches into the interpreter once per element, which is where the ten to one performance difference this project exists for disappears. firepanda raises at construction, naming the column and the offending Python type, so the user finds out at the point they can still fix it rather than after their program is written.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

## engine/inplace

The inplace parameter does not save a copy in pandas either, it only hides the assignment, and it makes every call site ambiguous about whether it returns a frame or None. It also makes a chained call silently do nothing. firepanda raises TypeError with the reassignment form in the message, so the fix is visible in the error itself. This affects 42 pandas callables and every one of them has the same one line fix.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

- `divergences/inplace/*`

## engine/implicit-index

pandas gives every frame an index whether or not anybody asked for one, and then performs operations against it, so loc reads as a label lookup on numbers that are actually positions and reindex against a label nobody declared returns a row of nulls. firepanda has no implicit index, so the operations that need one either take an explicit key or work positionally, and the places where that is visible are fewer than the size of this decision suggests.

**Instead.** there is no index unless one was declared. loc takes a declared key or raises, reindex against undeclared labels raises rather than manufacturing null rows, and reset_index has nothing to move into a column.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

- `divergences/implicit-index/*`

## engine/regex-lookaround

firepanda's regex engine has RE2 semantics, which give a linear time guarantee in exchange for dropping backreferences and lookaround. Both of those constructs need backtracking, and backtracking is what lets one adversarial pattern take exponential time. On a hundred million rows that is not a slow query, it is a hung process. A pattern using either raises with the offending construct named, because the pattern is unsupported rather than invalid and those are different words to the person reading the message.

Kind `engine`, since 2026-09-04, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

- `divergences/regex/*`

## engine/moment-precision

The variance, the standard deviation, the standard error and the skewness are computed from deviations around each group's mean, and the mean is a sum divided by a count, so it is near the true mean and is not it. pandas leaves that error in. firepanda sums the plain deviations alongside the squared ones and subtracts the residual, which costs one addition per row and makes the answer independent of how accurate the centre was. On ordinary columns the two agree to the last bit and the correction is worth nothing. On a column of large values with a small spread it is worth a great deal, and the two engines part company: on five values at two to the fifty second pandas gives a variance of 37.25 where the true value is 37.2, and a skewness of 1.4863469519931585 where the true value is 1.3253147098134046, which is twelve percent. On the suite's own int64 corpus frames, where the groups are large enough that numpy's pairwise summation gives pandas a better centre than firepanda's plain accumulation does, the correction moves firepanda towards pandas rather than away: pandas is 5.9e-6 from the true skewness of int64_half_null and firepanda is now 1.2e-16. This entry exists because on the shape of column above, and only on that shape, firepanda answers something pandas does not.

**Instead.** the moments are corrected for the centre they were measured around, so the answer does not change when a constant is added to the column. Where the two disagree, firepanda is the one nearer the value exact arithmetic gives.

Kind `engine`, since 2026-09-05, specified in `06-pandas-parity.md#the-genuine-omissions`.

Asserted by:

- `divergences/moment-precision/*`

## engine/zero-divisor

Dividing an integer by zero has no answer, and the two engines disagree about what to write in the row that has none. pandas promotes the whole column to float64 and writes an infinity or a NaN, which costs every other row in that column its type: an int64 column with one zero divisor in it comes back float64, and every value in it above two to the fifty third is then silently rounded, so one bad row damages the good ones. firepanda writes a null, which is the value the format already has for a row with no answer, and keeps the column's width, so the rows that divided exactly stay exact. True division is not affected and is not registered here, because its answer is a float64 whatever the divisor is and there is no type to lose. The bool remainder is the one place this is visible outside the integer widths: pandas answers int8 zeros for `flag % flag` because the bool path skips the masking it applies to the integer dtypes, and firepanda widens to int8 and answers a null at the zero divisor like every other integer column.

**Instead.** the row divided by zero is null and the column keeps the dtype it started with. Floor division and the remainder on an int64 column answer int64, and `flag % flag` on two bool columns answers int8 nulls rather than int8 zeros.

Kind `engine`, since 2026-09-06, specified in `06-pandas-parity.md#the-genuine-omissions`.

## engine/category-code-width

pandas picks the width of a categorical's codes from how many categories there are, so a column of three categories gets int8. firepanda writes int32 whatever the count is. Picking from the cardinality means the same column encodes to a different Arrow type on different data, so a program that reads the codes has no type to write down and a file written on Monday does not have the schema of the one written on Tuesday. It is also visible through the Arrow export, which is the boundary this library is built on, so it is a decision about the dtype vocabulary rather than one about the encoder. The values agree either way, and a program comparing codes to codes is unaffected. The one that is affected is a program comparing dtypes, and that program is better off finding out.

**Instead.** the codes are int32 whatever the number of categories, and a code for a row whose category is missing is null rather than the sentinel minus one, because firepanda's codes are an Arrow column with a validity bitmap and pandas' are a numpy integer array with nowhere to record absence.

Kind `engine`, since 2026-09-11, specified in `27-what-a-caller-does-with-a-category.md#three-differences-from-pandas-all-of-them-deliberate`.

Asserted by:

- `categorical/codes`

## engine/comparison-null

Comparing a missing value to anything has no answer. pandas writes False, because the result of a comparison in pandas is a numpy bool array and a bool array has two values and nowhere to say a third thing. firepanda's result is an Arrow column with a validity bitmap, so the row that had no answer is missing rather than false. This is the whole library and not the category columns: it is already what a text or a number column answers, and the reason the category cases are the ones registered here is that they are the ones the suite currently runs. The difference matters to a caller who counts the False rows, since the pandas count folds the rows that were missing in with the rows that genuinely did not match, and there is no way back from that number to either one.

**Instead.** a row whose value is missing compares to null rather than to False, so the result has three states and the caller can tell a row that did not match from a row that had nothing to match. A category column inherits this from the rest of the library rather than restating it.

Kind `engine`, since 2026-09-11, specified in `28-comparing-a-category.md#nulls-follow-the-library-rather-than-pandas`.

Asserted by:

- `categorical/compare-eq`
- `categorical/compare-lt`

## engine/string-count-width

How many characters a row has and where a substring sits in it are both integers, and both are unanswerable on a row that is missing. pandas has nowhere to put that in a numpy int64 array, so it widens the whole column to float64 and writes a NaN, and every count in the column becomes a float because one row had nothing to count. firepanda answers int64 with a null in that row, which is the type the question has and the value the format already has for a row with no answer. The cost of the pandas answer is not theoretical: a position above two to the fifty third does not survive the trip through a float, and a caller who wanted to index with the number gets a float back and has to cast it. A column with no missing rows in it is int64 in pandas too, which is why this entry names one frame: on the other three text frames the two engines agree to the last bit and the suite requires them to.

**Instead.** str.len, str.find and str.rfind answer int64 with a null on a missing row, rather than float64 with a NaN. The counts and positions themselves agree.

Kind `engine`, since 2026-09-11, specified in `30-a-position-in-a-string.md#the-library-already-counted-and-it-counted-bytes`.

Asserted by:

- `strings/len`
- `strings/find`
- `strings/rfind`

On the `strings_null_heavy` frames only. On the others the two engines agree exactly, and the suite requires them to.

## engine/string-predicate-null

Asking whether a missing string starts with a letter has no answer, and firepanda writes a null for the same reason engine/comparison-null gives: the result is an Arrow column with a validity bitmap and there is a place to say so. pandas writes False, and the road it takes there is worth naming because it is not the numpy one the comparison entry describes. pandas has two string backends. Its default str dtype carries missing values as NaN and its predicates fill those rows with False deliberately, while its own nullable string dtype answers NA and agrees with firepanda exactly. So this is a difference from one of pandas' two answers rather than from both, and a user who wants the firepanda behaviour in pandas can already have it by asking for the other dtype. It matters to anyone counting the False rows, since that count folds the rows that had no answer in with the rows that genuinely did not match and there is no way back from the number to either one.

**Instead.** str.startswith and str.endswith answer null on a missing row rather than False, so the mask has three states and a caller can tell a row that did not match from a row that had nothing to match.

Kind `engine`, since 2026-09-11, specified in `30-a-position-in-a-string.md#the-library-already-counted-and-it-counted-bytes`.

Asserted by:

- `strings/startswith`
- `strings/endswith`

On the `strings_null_heavy` frames only. On the others the two engines agree exactly, and the suite requires them to.

## engine/window-infinity

pandas cannot get an infinity back out of a window and firepanda can, and there are two separate reasons for that rather than one. A rolling or expanding sum is carried from one row to the next, so pandas' running total goes infinite the moment an infinity enters the window and goes to NaN when that row is subtracted again, and it has no way back. Measured on pandas 3.0.5, the expanding sum over the suite's own float64 frame answers the largest finite double from row five onward, where the window holds both a positive and a negative infinity and the arithmetic says NaN, and it answers that same finite number where the window holds only one of them and the arithmetic says an infinity. The extremes lose the same two values for an unrelated reason: pandas seeds its running maximum with negative infinity and reads a result equal to the seed as an empty window, so an expanding max over a column whose second row is a positive infinity answers the largest finite value it has seen instead, for every row after it. firepanda counts the two infinities beside the finite total and assembles the answer from the three at the end, and its extremes treat an infinity as the ordinary value it is, so both survive the row that carried them leaving the window again. pandas' exact recovery rule could not have been copied even if copying it were the right thing to do, because pandas ships its window kernels compiled and their source is not in the wheel.

**Instead.** a window that holds an infinity answers that infinity, a window that holds one of each sign answers a NaN, and both are still right after the row that carried the infinity has left the window again. Every window with no infinity in it agrees with pandas to the last bit, which is why this entry names two frames and not the other two the same cases run on.

Kind `engine`, since 2026-09-11, specified in `31-a-window-is-a-pair-of-rows.md#why-the-reductions-are-carried-and-what-that-costs`.

Asserted by:

## engine/window-infinity-dense

The difference engine/window-infinity describes, on the seven cases where it is only visible on the frame with nothing missing in it. Each of these asks for a four or five row window and does not set min_periods, so the window has to hold as many values as it has rows before it answers at all. The half null corpus frame has a missing value in every other row, so a window that narrow never fills, both engines answer NaN in every row, and the suite requires them to agree there. On the frame with no nulls the windows do fill, they reach the positive infinity in row one and the negative infinity in row two, and the two engines part company for the reasons the other entry gives. This is a second entry rather than a longer case list on the first one because an entry narrows to frames as a whole rather than case by case, and folding these seven in would have told the suite that a five row window over a half null column has to differ from pandas, which is the opposite of what is true.

**Instead.** a window that holds an infinity answers that infinity and a window that holds one of each sign answers a NaN, the same as engine/window-infinity. On the half null frame, and on the int64 and tall frames these cases also run on, there is no infinity in reach and the two engines agree exactly.
