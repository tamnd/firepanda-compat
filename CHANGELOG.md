# Changelog

All notable changes to this repository are recorded here. The format is
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and this repository
follows [semantic versioning](https://semver.org/spec/v2.0.0.html), where the
public interface is the case id namespace, the result file schema and the
divergence registry format.

## [Unreleased]

### Added

- The stats section in the driver, 16 cases, and the cleanest result this suite has produced about firepanda so far. Almost every case in this section answers with a scalar, and a scalar does not go through an index, so this is the first section where firepanda's arithmetic is compared to pandas without issue #154 standing in front of every result. 36 pass, 19 fail, 51 unimplemented over 106 runs, and the 19 failures are not 19 problems. Thirteen of them are firepanda issue #170 wearing two hats. Eight are a reduction with nothing left to reduce coming back as a null where pandas gives NaN, which is `std`, `var`, `sem` and `skew` over `float64_all_null`, the single row standard deviation, the median and the quantile of an all null column, and a correlation with no complete pairs. Five are the other half of the same question: `float64_no_nulls` holds one NaN and two infinities despite its name and `float64_half_null` holds 33 NaNs on top of its 32 nulls, pandas drops a NaN before it sorts and firepanda sorts it as a value, so two medians, two quantiles and `hasnans` disagree. Neither half is a bug, both are the decision in #170, and this section is the first place the cost of that decision has a number on it. Two more failures are the Arrow reader refusing a dictionary encoded column, which is #159. Two are `Series.argsort` coming back as uint32 where pandas gives int64. The last one is `skew` on the two int64 frames, and it is the interesting one.
- `sem` and `skew` in the driver, and with them the first case where this repository asked for a reduction, firepanda did not have it, it was written, and the number moved. The flat groupby family was 44 pass and 4 unimplemented; it is 48 pass and 0 unimplemented. The four were not disagreements about an answer, they were absences, and they are the whole reason to run a conformance suite against a library still being built. firepanda pull request #175 has the kernels. The section total goes from 50 pass, 58 fail, 65 unimplemented to 54 pass, 62 fail, 57 unimplemented: the four new passes are the flat forms and the four new failures are the indexed forms, which now produce an answer where they used to produce nothing and fail it on the index shape like the other 55. Of the 62 failures, 59 are firepanda issue #154 and the remaining 3 are one thing, the Arrow IPC reader refusing a dictionary encoded column, which is every `observed` case on the two categorical frames.
- The groupby section in the driver, and with it the first evidence that firepanda's grouped arithmetic is right. Running the section as it stood produced 58 failures of which 55 said only "index names (), expected ('key',)", and that is all they could ever say, because the comparison returns as soon as the two sides have different numbers of index levels and never reaches a value. A section that cannot tell a correct grouped sum from a wrong one is not measuring the thing its name says. So there is now a `flat-` case beside each aggregation, asking pandas for the same reduction with `as_index=False`, which is the shape firepanda produces, and firepanda passes 44 of those 48 runs. The four that do not are `sem` and `skew`, which firepanda does not have. Sum, mean, min, max, count, first, last, median, nunique, std and var all agree with pandas exactly across four key frames including the awkward one with a null key, an empty string key and two keys differing only by case, and so do the null keeping and unsorted forms and the two key grouping. The section total is 50 pass, 58 fail, 65 unimplemented, and every one of the 55 shape failures is firepanda issue #154 and nothing else.
- Twenty six more cases in the firepanda driver, two more answer kinds in the protocol, and the findings that came out of them. The basics section went from 55 pass, 18 fail and 341 unimplemented to 120 pass, 57 fail and 237 unimplemented, which is the first time the number moved because the instrument got better rather than because the library did. `index` and `tuple` join `scalar`, `frame` and `series` as answer kinds, because `df.columns` is an Index and `df.shape` is a tuple and neither is a Series, so folding them into one would score a real difference as a pass. The new failures sort into four piles and none of them is a surprise: sixteen are operations whose answer keeps a non default index, which firepanda has no index to keep, eight are the integer dtype question in firepanda issue #171, most of the rest strengthen the NaN as missing question in firepanda issue #170, and one is a real bug, `head(-2)` returning nothing where pandas returns all but the last two rows, now fixed in firepanda pull request #174.
- `drivers/firepanda/build.sh` takes the library checkout and the toolchain checkout as separate arguments, defaulting to the same one. The loop this repository exists to support is to find a conformance failure, fix it on a firepanda branch, rebuild the driver and see whether the number moved, and the sane place to hold that branch is a git worktree, because the main checkout usually has somebody else's work in progress in it. A worktree has no pixi environment of its own, and installing a second copy of the same pinned toolchain to compile a branch of the same library is minutes of downloading for nothing. The stamp still takes the version, the commit and the dirty flag from the library checkout, since that is the one that decides what was measured, and notes the borrowed toolchain next to the Mojo version so a result file cannot quietly claim otherwise.
- The firepanda driver, and with it the first conformance number this repository has ever produced against something other than pandas. `drivers/firepanda/main.mojo` runs the firepanda spelling of a case and writes the answer as Arrow, `fpcompat/driver.py` reads it back into the same `Answer` the pandas side builds, and nothing downstream of `compare` can tell the two forms of the subject apart. On the basics section, 414 runs: 49 pass, 24 fail, 341 unimplemented. Every one of those 24 is a statement about firepanda and the list is in firepanda issue #8. The build is `pixi run driver`, it uses the Mojo toolchain pinned by the firepanda checkout rather than one pinned here, and it stamps the version and commit it built against so that the result file can say which firepanda produced it.
- A comparison that sorts in Arrow rather than in the interpreter, and a second clock on every result record. The oracle took 195 seconds while the per case timings in the file it wrote summed to 5.1, because the clock stopped before the comparison started and roughly 160 seconds were going into a sort that rendered every value to a string and sorted Python tuples, on six merge answers of ten million rows each. Arrow sorts the key columns now and the rendered sort remains for the dictionary encoded and nested columns Arrow refuses, with both sides of a comparison always taking the same path. The oracle is 195 seconds down to 14 and the relaxation sweep 139 down to 39. `compare_seconds` is on every record and totalled on the document, so the next time the two numbers diverge the file says so.
- The relaxation sweep, `pixi run sweep`, and the correction to the specification that came with it. `05-comparison.md` said the oracle would be run a second time with each relaxation individually disabled and the cases that then failed would be the ones needing it. Measured: 18 case and relaxation pairs, run with their relaxation off, zero failures, because pandas against pandas returns both sides in the same order and an order relaxation has nothing to absorb. Under the specified rule every declaration in the repository was unnecessary and would have been deleted. The sweep reorders the oracle's own answer instead and requires each declaration to be what makes the case pass against it. All 18 declarations are load bearing.
- The specification, 12 documents in `docs/specs/`, mirrored from the author's notes.
- The scaffold: pixi environment pinned to pandas 3.0 and pyarrow 25, CI, licence.
- The surface tool, which counts the pandas API rather than remembering it, and the committed inventory of pandas 3.0.3 that every coverage number is computed against.
- The corpus, 56 frames generated from one seed, described by a committed manifest and never committed as data.
- The comparison layer, which decides what the same answer means, with four tolerance classes and a closed list of relaxations that each have to say why.
- The case registry and the runner, 623 cases over 1429 runs, four outcomes and no skip, one engine per process, and a worker crash attributed to the case that caused it.
- The surface sweep: 1413 generated L0 cases and 1034 generated L1 cases, one per name and one per readable signature, so that the two cheapest levels are measured over the whole of pandas rather than over the names somebody thought to check.
- The scoreboard, which reports against the pandas surface rather than against our own case list, prints the parameter coverage next to the score so that neither number can be quoted alone, and refuses a pull request that lowers a section without editing the recorded floor.
- The divergence registry, where a registered divergence has to actually diverge: 7 entries, 68 cases asserting them, a generated public page, and a build that fails when an entry stops being true.
- The cost matrix, 65 operations of which 21 are chains, one process per engine per operation, seven repeats with the median and the interquartile range, and a per machine baseline with a ten percent regression gate. It runs on its own corpus, which is the correctness generator and seed at one million rows.
- `operations.json`, the cost matrix operation table with the numbers taken out, committed and checked in CI so that firepanda-bench can link a query to the operations it is made of without depending on this package.
- Eleven cost matrix rows that came from firepanda-bench rather than from the parity sections, because linking each benchmark query to its operations found eleven that a published query runs and the matrix had no row for. `GroupBy.median` is the one that mattered: it keeps its values per group, and until it existed the matrix measured no reduction with per group memory in it at all.

### Fixed

- An order relaxation over a string view column raised out of pyarrow rather than reordering. Arrow's `take` has no kernel for the view layouts, so the runner wrote "the comparison itself raised" into the result file, which is the harness admitting a bug of its own in the place a reader goes for facts about the engine. firepanda's strings are views, so this was every grouped comparison on a text key rather than an exotic corner. View columns are widened to their large variants before the take, which loses nothing, since `canonical_type` already folds all three string widths into one name on the grounds that pandas has one string dtype.
- A comparison between two answers with different numbers of index levels raised `IndexError` out of pyarrow instead of reporting a difference, because the column loop is indexed by the pandas side's shape and ran off the end of the narrower one. It was found the first time a real subject produced an answer with no index, which is `DataFrame.tail` against firepanda, and until it was fixed the runner reported it as a bug in `fpcompat.compare`, which it was.
